## M1 (medium) — Pg item writers skip B7's `FOR SHARE`

`crates/htui-store/src/pg/write.rs` `mint_item` (about `:2894`) and `update_item` (about `:3019`) check the item's
target with a lock-free `EXISTS (... t.retired_at IS NULL)`. The level setters lock through `share_level_target`.
Race: `retire_target` holds `FOR UPDATE`, scans users (none); an `update_item` whose snapshot still sees
`retired_at IS NULL` passes the guard, its FK check waits on the lock and succeeds after the retire commits: the item
names a retired target (D14 forbids). If `delete_target` wins instead, the FK raises a raw `23503`/`23001` that
`map_sqlx` passes as `Constraint("fk_item_target: …")`, breaking P9. The reviewer reproduced the retire variant on
PG 18; with `FOR SHARE` inside the `EXISTS` the guard fired.

Fix: append `FOR SHARE` to both `EXISTS` subqueries (or run each writer in a transaction calling
`share_level_target(…, "item.target_id", …)` first; pick the one that fits the existing statement shape). The existing
zero-row follow-up reads already produce `target_retired` / `references_no_row`. Check that `mint_item`'s CTE
(`INSERT … SELECT`) accepts the `FOR SHARE` form; if not, use the transaction form there.

Test: in `crates/htui-store/tests/it/pg_criteria.rs`, add `an_item_write_behind_a_retire_is_refused`, modelled on the
existing `a_level_set_behind_a_retire_is_refused` (which covers `set_project_target`): drive `update_item` and
`mint_item` behind a held retire and assert `target_retired`, never a stored retired target.
