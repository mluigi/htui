## Medium

**M1. `reopen_trees` leaks the reacquired guard on a store error.** `engine.rs` ~:5701 calls `reacquire`, then
~:5703 reads `repos(..)?`. `resumed_member` sets `*trees` only after `reopen_trees` returns (~:5802), so
`run_part`/`run_candidate` do not release the guard. They fail the member and answer `Ok`, and the round goes on.
Under `shared_serialized` the sibling's `prepare` then waits forever on the non-reentrant per-repo lock
(`isolate/real.rs` ~:551-569).
**Fix:** do every fallible read before `reacquire`, or release on the error path. Add a test using a store or fake
seam that fails that read.

**M2. `labels_between` refuses valid resumes.** In `isolate/git.rs` ~:1911 and `isolate/real.rs` ~:653-666,
`prepare_worktree` creates `htui/<W>` at the source checkout's current HEAD (`real.rs` ~:787-800). A worktree that
never committed keeps that branch after removal (pinned at `real.rs` ~:2828). So any worktree-mode step of any run
on the same repo, prepared while stopped step S's checkout sits above S's base, puts a label on `base..HEAD`. That
happens even while S was still running. S's resume then fails `moved_while_stopped`, and a plain step's
`fail_hard` fails the run.
**Fix:** the reviewer prefers comparing HEAD against a HEAD kept at stop time instead of scanning labels. That needs
somewhere to keep it: use an existing tree-row field only if one already fits, because a migration is not allowed.
Otherwise make the scan ignore labels that only mark a worktree-step branch point (`htui/<W>` refs for worktree
steps), and state the residual gap in the report.
Tests: a no-commit worktree step on the same repo must not refuse the resume, and a real foreign move must still
refuse it.

## Low

  reads the same function.

  resumed in one pass then get different `live`, so `command_run` exposure differs under `fan_out_only`
  (`kind.rs` ~:63-71). Count `Stopped` as live in a running run. `drive_group`'s `live` reads it the same way.

  `Resume` resumable for `run_resumable`. Then add a conformance case.
