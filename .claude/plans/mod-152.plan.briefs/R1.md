## Findings

**F1 (medium) — `command_wait` slices before it scrubs; a live wait does not fail closed.**
`crates/htui-mcp/src/tools/command_async.rs` `seen` (~567-576): live rows hand `seen` raw complete
lines; it cuts the tail (`slice(.., Mode::Tail(20), 4 KiB)`) and the `after_line` region, then scrubs
each window. A secret straddling the 4 KiB `cut_tail`, or PEM body lines whose header is above the
window (the PEM rule needs the header/footer, `htui-core/src/scrub.rs:134-142`), leak in `tail`/`line`.
`command_output_read` scrubs the whole text first (`command_log.rs` ~525-528) and is correct.
*Fix:* scrub `view.text` once as a whole (withheld marker on failure), then compute `tail`, the
pattern region and `line` from the scrubbed text. Match the pattern on scrubbed text only (unchanged).
*Test:* a live command printing a multi-line PEM key whose header is above the 20-line tail →
`command_wait` returns no key body line; a known secret straddling the 4 KiB cut of a long last line is
not returned.

**F2 (medium) — live line numbers shift once output passes 2 MiB.**
`command_log.rs` `LogBuffer::tail` (~446-458), `complete_lines` (~465), consumed by `seen` and
`command_wait`. Past the cap each snapshot is a sliding window with the marker as line 1, so an
`after_line` taken from the previous `next_line` skips the k lines dropped in between.
*Fix:* `LogBuffer` counts complete lines dropped from the front; `after_line`, `line_no`,
`next_line`, `first_line`/`last_line` and `total_lines` are absolute line numbers of the command's
output (line 1 = the first line it printed). The stored log records the same offset so a read after
the command ended numbers lines the same way: add `first_line_no` to the stored text's header or
derive it from `total_bytes`/a counter — pick the smallest change; if it needs a store column, do NOT
add a migration in this round: carry it inside `CommandLog` text-free metadata only if that already
exists, otherwise answer `first_line` relative numbering for stored logs and document it. State the
choice in the report. Update `docs/htui-mcp.md` ("Lines are those of the log, counted from 1").
*Test:* a command printing > 2 MiB then a marker line; a wait with `after_line` = the previous
`next_line` matches the marker line.

**F3 (low) — `command_output_read` reads the store before the live snapshot.**
`command_log.rs` ~91-101. Store read sees `running`/no log; the task then writes the log, finishes,
`Live::end`s; the snapshot is filtered out as ended; fallback is the stale `None` →
`not found: command log` for a row that just finished.
*Fix:* take the live snapshot first (as `Source::view` does), or re-read the store when the snapshot
says ended. *Test:* unit test over the ordering if it can be made deterministic; otherwise reason it in
the report.

**F4 (low) — registry entries are never removed.**
`command_async.rs` ~174, ~190. Ended `Live` entries stay for the session's life; `reserve` scans all.
*Fix:* keep at most `ENDED_KEEP = 64` ended entries (drop the oldest ended first); `command_cancel`
on a pruned id of this session answers from the store — keep a session-owned set of started ids so
scope stays "this session's rows" (an id never started here is still `not found`). *Test:* start and
finish > 64 commands (cheap `true`), the registry holds ≤ 64 ended, and `command_cancel` on the first
id answers its stored terminal status.

**F5 (low, performance) — a running wait redoes up to 2 MiB of decode+scrub every 200 ms.**
`command_async.rs` ~135 (`snapshot`), ~567; `command_log.rs` ~465.
*Fix:* cache the decoded+scrubbed view keyed by `LogBuffer.total` (F1's single scrub makes this
natural); decode outside the std `Mutex` (clone the bytes, release, then decode); run `into_stored`'s
2 MiB scrub under `tokio::task::spawn_blocking` (or `htui_agent::contained::spawn_blocking`).
No new test beyond F1's; existing tests must stay green.

**F6 (low) — a single line over 2 MiB is stored from mid-line.**
`command_log.rs` ~456-458 (`tail`), and `cap_tail`. When the cut lands mid-line and the kept bytes
hold no newline, the kept bytes start mid-token, so a known secret straddling the cut is scrubbed as a
fragment and its suffix survives.
*Fix:* when the cut is partial and the kept bytes hold no newline, keep nothing before the marker
(the line is dropped, not split). *Test:* one 3 MiB line carrying a secret across the cut → the
stored text is the marker only (or marker + nothing of the split line).
