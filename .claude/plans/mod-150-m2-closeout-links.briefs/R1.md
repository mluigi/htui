## M1 (medium): an agent can withdraw the link while the close-out runs (Pg)
- **The race:** an unnamed `duplicate` close-out reads the item's live outgoing `duplicates` link. An
  unnamed `superseded` close-out reads a live incoming `supersedes` link. A step of a cancelled or
  finished run can still `withdraw_link` under `StepFence::Unleased`, and `withdraw_link` takes no item
  lock. Both transactions commit, and the item is closed as `duplicate`/`superseded` with no live link.
- **Wrong premise in D4:** the plan says "an outgoing `duplicates` cannot be withdrawn concurrently".
  That is false.
- **Fix (maintainer's choice: lock the link row):**
  - In `PgStore::close_out`'s unnamed checks, lock the live link row the decision rests on with
    `FOR SHARE`, in both the `duplicates` and the `supersedes` branch.
    - A concurrent `withdraw_link` UPDATE then waits for the close-out to commit.
    - With `LIMIT 1`, lock one live row. That is enough: the rule needs at least one live link.
  - Withdrawing after the close-out commits stays allowed, as it is in MemStore. The MemStore state
    lock already serialises the two, so it needs no change.
  - Add a pg_criteria race in the style of `a_close_out_naming_a_canonical_races_an_agent_proposal`:
    an unnamed `duplicate` close-out against a concurrent `withdraw_link` of the item's only
    canonical.
    - After each round, either the item is closed and the link is live at the moment of the close
      (the withdrawal lands after it, as a tombstone), or the close-out was refused with
      `close_out_needs_a_link`.
    - The case that must never happen: closed as `duplicate` with the link tombstoned *before* the
      close committed. Assert it through ordering: the withdrawal's `deleted_at` is not earlier than
      `closed_at`, or use an equivalent check.
  - Rewrite D4's sentence in the plan file
    (`.claude/plans/mod-150-m2-closeout-links.plan.md`, the D4 bullet "An outgoing `duplicates`
    cannot be withdrawn concurrently…") so it describes the row lock.

## L1: two close-outs naming each other deadlock (Pg, 40P01)
- **The deadlock:** close-out x holds `x FOR UPDATE`, and its link insert's foreign key needs
  `FOR KEY SHARE` on y. Close-out y does the mirror image. Any pairing deadlocks: dup/dup, sup/sup or
  dup/sup.
- **Fix:** when `names` is `Some`, take the two row locks in id order.
  - Lock the smaller id first: `FOR UPDATE` on the closing item, or `FOR KEY SHARE` on the named
    item, whichever is smaller.
  - The duplicates advisory lock stays the first statement (D4 deviation, required).
  - A missing named item must still answer `NotFound` at its place in D2's order.
- **Test:** a pg_criteria round with two concurrent close-outs naming each other, for example x as
  `duplicate` of y and y as `superseded` by x. Both must commit or get a store-level refusal, never
  40P01.

## Nits
- **Explicit `Duplicate` arms:** `close_out_needs_a_link` (`htui-core/src/store/traits.rs`),
  `naming_question` and `needs_a_name` (`runs.rs`) use a `_ =>` arm over `Resolution` for the
  `duplicate` case. Match `Resolution::Duplicate` explicitly. For the other resolutions, keep a
  sensible arm: unreachable by contract, so use whatever fits each function's return type, without a
  panic in production code.
