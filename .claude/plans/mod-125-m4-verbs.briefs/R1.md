## Apply

1. `docs/htui-cli.md` ~:560 says a confirmation without a terminal is "refused before anything is printed or
   written". The headless connect runs first (its bootstrap can register the box; `load_or_mint` can create
   `box.toml`). Reword: refused before the stop (or resume) is written.
2. `docs/htui-cli.md` ~:551 says each command prints the report before it writes; `--yes` skips that preview.
   Add "(not with `--yes`)" or equivalent.
3. `CONCEPTS.md:67`: "or is cancelled when that box no longer can" reads as if htui cancels it. Code only reports
   `cannot be resumed: cancel it from the Runs pane`. Reword to "...or, when no box can, can only be cancelled
   [R-ORCH-16]". Follow `.claude/rules/concept-docs.md` (both copies exist; read it) for the Reviewed line.
4. `crates/htui/src/stop_cmd.rs` ~:356 with ~:400-402: the stop's `requested_at` is `ctx.now`, taken before the
   interactive prompt, so a prompt left open for ten minutes records a stale time. Take the time after `confirm`
   (e.g. a `now: fn() -> DateTime<Utc>` in `Context`, tests pin it), right before `stop_workspace`.
5. `stop_cmd.rs` ~:433-450: `htui resume` deletes whatever stop row exists at write time, even one written by
   someone else while the prompt was open (A reads graceful stop; B resumes; C forces a new stop; A answers y and
   deletes C's forced stop). After `confirm`, re-read `workspace_stop`; if it is gone or its `mode`/`requested_at`
   differ from what the preview showed, write nothing and refuse (exit 2) with a line saying the stop changed while
   asking and to run `htui resume <slug>` again. Apply the same re-read to `htui stop`'s escalation path if it is
   equally cheap (escalating a row that was resumed meanwhile would create a fresh forced stop the user did not
   preview: refuse the same way). No store change. Unit-test both over `MemStore` (a prompt seam that mutates the
   store before answering yes, or the equivalent the existing `Answer` seam allows).
6. `crates/htui/tests/it/stop_cli_pg.rs` ~:136-215: the module doc claims the report reads caps through PgStore,
   but no case has a stopped step, so the Postgres path of `run_steps`/`step_events`/forecast never runs. Give the
   `stopped_on_the_box` run one running agent step with a `session_started` banner row (and an agent whose caps
   resume) before `stop_run`, and assert its line says `reopens its agent session`. If building that on Postgres
   turns out disproportionate, reword the module doc instead and say so.
7. `stop_cmd.rs` ~:555-592: no test shows the wait ends early once the runs settle (a `settle` that always waited
   `ctx.wait` would pass). Add a paused-time test (or short real durations) where a spawned task settles the
   running run (`stop_run` on its lease) after ~3 s with `ctx.wait` 20 s: assert it returns well under the bound,
   the header reads `stopped`, no `still stopping` line. Mind the repo memory: `start_paused` + a real child
   process do not mix; MemStore has no child, so paused time is fine.
8. `crates/htui/src/qdrant_cmd.rs` :208, :218: `dsn_exit` and `failure_exit` were made `pub(crate)` but nothing
   outside `qdrant_cmd` uses them; make them private again (keep `connect` `pub(crate)`).
9. Nit, `crates/htui-orch/src/promote.rs`: `stopped_step_resume` compares `fanout_index` with a literal `-1`;
   declare a module-local `const JUDGE_FANOUT_INDEX: i32 = -1;` as `recover.rs:186` and `status.rs:471` do, and use it.
