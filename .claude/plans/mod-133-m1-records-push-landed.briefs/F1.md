## L1 (low): Postgres `take_integrations` can deadlock against itself

`crates/htui-store/src/pg/write.rs` (around 9972-10010; find `fn take_integrations`). The take is one
`UPDATE integration g ... FROM run r WHERE ...` with no `FOR UPDATE SKIP LOCKED`. The plan (D6) asked for
SKIP LOCKED or an equivalent; the repo's sweep rule is that a sweep never waits on a row lock (see the
blueprint A-5 comment near `write.rs:7598-7600`, and `prune_finished_entries` locking in `item_id` order).
Scenario: the walk's `take_integrations(.., Some(run))` and the sweep's `take_integrations(.., None)` on one
box run at once over two records of one run; each update visits rows in a different order and Postgres
kills one with `40P01`.

Fix: lock the candidates first, in a fixed order, skipping held rows, then update only those:

```sql
WITH c AS (SELECT g.run_id, g.repo_id FROM integration g JOIN run r ON r.id = g.run_id
            WHERE <today's predicates, unchanged> ORDER BY g.run_id, g.repo_id
              FOR UPDATE OF g SKIP LOCKED),
     taken AS (UPDATE integration g SET <today's SET list> FROM c
                WHERE g.run_id = c.run_id AND g.repo_id = c.repo_id RETURNING g.*)
SELECT ... FROM taken ORDER BY run_id, repo_id
```

Keep every predicate (pending, executing box, run filter, lease free/own/expired by `clock_timestamp()`),
the TTL check, the returned columns and the `(run_id, repo_id)` order. The existing
`pg_concurrent_integration_takes_lease_each_record_once` test must stay green; add a test that two
concurrent takes by different owners (one with a run filter, one without) over two records of one run
both return `Ok` (no deadlock error) and together lease each record at most once. Regenerate `.sqlx` for
the changed query.

## L2 (low): `write_integrations` doc comment overstates parity with MemStore

`crates/htui-store/src/pg/write.rs` around 2671-2695 (`write_integrations` or the helper `finish_run_on`
calls). The comment says a malformed snapshot entry writes nothing "as MemStore's decode of the same value
would find no entry". In fact Mem decodes the whole map at once (one bad entry → no records at all), while
Pg filters entry by entry, and Pg casts each key with `e.key::uuid`, so a non-UUID key fails
`finish_run(Done)`. Production cannot reach this (the snapshot is serialised from a typed map). Fix: reword
the comment to say what each store does. No behaviour change.
