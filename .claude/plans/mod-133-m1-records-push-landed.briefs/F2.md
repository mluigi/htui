# MOD-133 M1 fix round F2: landing robustness (orch + worker)

Context: MOD-133 M1 is implemented on `hr/MOD-133` (range `c0bec951..HEAD`). The plan is
`.claude/plans/mod-133-m1-records-push-landed.plan.md`; read only its D8-D10 sections if you need them.
The final reviewer reported the findings below. **Confirm each against the code before acting**; if a
finding is wrong, say so in `rejected_findings` with the evidence and do not change the code for it.
Product constraints that stay: never force a push; never prompt (`GIT_TERMINAL_PROMPT=0`, ssh batch mode);
an authentication failure parks the record as a typed refusal naming the (redacted) remote; an isolator
`Err` leaves the record `pending`; credentials never reach reasons, notes or logs.

## M1 (medium): an unreachable remote stalls the sweep's admission and claims

`crates/htui-worker/src/runtime.rs` (~2278, the land arm sits before `admit`/`claim_scan`; ~2341),
`crates/htui-orch/src/isolate/real.rs` (~2172), `crates/htui-orch/src/isolate/git.rs` (`VERB_TIMEOUT` 120 s).
When a remote stops answering (packets dropped), ssh (no `ConnectTimeout`) or curl run to the 120 s verb
budget; `ls_remote` returns `Err`; the record stays pending and the next sweep takes it again. Sweeps run
one at a time and the arm is awaited before `admit` and `claim_scan`, so with k such records every sweep
waits ~k x 120 s before admitting or claiming anything, for as long as the outage lasts.

Fix, all three:
1. Move the land arm in `sweep_once` to after `claim_scan` (still run every sweep, unconditionally once
   I-1's executor check has passed; mind any early return in the claims path).
2. In `land_taken` (htui-orch engine), after an isolator `Err` for a remote, skip that pass's remaining
   records with the same remote (they stay pending; the same owner re-takes them next pass). Log once.
3. Bound the network verbs: ssh gets `-o ConnectTimeout=20` next to `BatchMode=yes`; the network verbs set
   `GIT_HTTP_LOW_SPEED_LIMIT=1000` and `GIT_HTTP_LOW_SPEED_TIME=30`; `ls-remote` runs under a 30 s budget
   (the push keeps the 120 s budget). Pin the env and budgets in the existing wrapper-git test.

## L1 (low): a transport failure becomes a permanent refusal

`real.rs` ~2178, `git.rs` ~1054. A DNS failure, connection refused or an HTTP 5xx makes `git push` exit 128
fast → `push_failed` → `refused` (M1 has no retry), while a slow outage of the same kind is `Err` and
retried. Fix: classify transport-level failures as `Err` (retryable), not a refusal: stderr `fatal:` lines
with `Could not resolve host`, `Connection refused`, `Connection timed out`, `Operation timed out`,
`The requested URL returned error: 5NN`, and `Could not read from remote repository` when no `remote:` line
precedes it and no auth marker is present. Auth failures (`Permission denied`, `Authentication failed`,
`could not read Username`, HTTP 401/403) stay refusals. Unit-test the classifier on these strings.

## L2 (low): `push_failed` drops the server's rejection reason

`git.rs` ~1054-1067. A protected-branch or pre-receive decline puts `!\t...\t[remote rejected] (reason)`
in porcelain stdout and `remote: error: ...` in stderr; `network_failure` reads stderr only and picks
`error: failed to push some refs to '<url>'`. Fix: prefer the porcelain `[remote rejected] (...)` reason,
else the first `remote: error:` line, else today's choice; still pass it through `scrub_remote`. Test it.

## L3 (low): a remote that already holds the run's tip and moved past it is refused `non_fast_forward`

`real.rs` ~2172-2183. After a crash between push and settle, someone pushes T→U; the retaking owner sees
`ls-remote` U != T and the push is rejected, telling the human to merge though the work landed. Fix: after
`ls-remote`, if the remote hash exists locally and the local tip is its ancestor, answer
`Landed { hash: tip }` without pushing (a local read: under `admin_guard`, inside `blocking`). No local
object → today's path. Test with a local bare remote advanced past the tip.

## L4 (low): `GIT_SSH_COMMAND` overrides `GIT_SSH` and `core.sshCommand`

`git.rs` ~1014-1025. Git ranks `GIT_SSH_COMMAND` above `GIT_SSH` and `core.sshCommand`; setting it
silently replaces a box's plink/`GIT_SSH` or configured ssh command. Fix: base command = inherited
`GIT_SSH_COMMAND`; else, if `GIT_SSH` is set, do not set `GIT_SSH_COMMAND` at all (leave `GIT_SSH` alone:
plink takes no `-o`); else `git config --get core.sshCommand` in the repo if set; else `ssh`. Append
` -o BatchMode=yes -o ConnectTimeout=20`. Document on the function that ssh takes the first value of an
option, so an inherited command already carrying `-o BatchMode=no` keeps it. Pin the cases in tests.

## L5 (low): a queued item refused with `IntegrateRefused` is skipped silently each sweep

`crates/htui-worker/src/runtime.rs` ~2605. `enqueue_in_batch` → `graph::resolve` → `IntegrateRefused` is
logged at debug ("the queue skipped an entry"); no note is written and the batch never drains. Fix: note the
item once (per batch, or once per distinct reason) the way `note_bad_cap`/`note_batch_stop` do, with the
refusal sentence. Test it with a project default `integrate: "bogus"`.
