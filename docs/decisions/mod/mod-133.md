## What the maintainer can do now

Each repo has an `integrate` mode, with a project default. The mode is frozen when a run starts, so changing it
mid-run never moves where that run lands. There are three modes:

- **`local`** (the default): unchanged. Steps merge into the primary checkout's current branch, and nothing is
  written about landing.
- **`push`**: after the run is `done`, the executing box fast-forwards the remote's target branch with its own git
  credentials. It never forces, never prompts, and pushes at most once (`ls-remote` checks first). A remote that
  moved, a checkout off the target branch, or a failed push parks the landing. That adds an item note, the item
  reads `↯ landing refused`, and a waiting row appears; `Unblock` retries it.
- **`pull_request`** (M3): the run's `worktree` and `copy` steps base on, and merge into, a run branch
  `htui/item/<key>` cut from the primary's `HEAD`. Your checkout's `HEAD`, index and files never move. After
  `done` the box pushes the run branch (never forced), and the record waits for MOD-134 to open the pull request.
  Settings still refuses `pull_request` until MOD-134 lands, so today it is reachable through the store and the API
  only.

A dependent item waits until its blocker's work has **landed**, at every readiness site (Postgres, MemStore, the
cache). While it waits, the blocker reads `⇡ landing`. The close-out summary has an `## Integration` table naming
mode, target and outcome per (run, repo).

## Milestone 1 - records, `push` and the landed check (`bfb2fd17..b8a4968f`)

- `IntegrateMode`/`IntegrationState` (`htui-core/src/model/integration.rs`). `repo.integrate` is nullable and falls
  back to a strict project default (`settings.integrate`). The modes are snapshotted at run start as
  `GraphSnapshot.integrate`, which is absent for `local`, so local snapshots keep their bytes.
- `finish_run(Done)` writes one `pending` `integration` record per non-`local` repo the run changed, in the same
  transaction.
- The executing box lands each record under a lease: right after `done` on the walk, and through a `sweep_once` arm
  as the recovery path. A landing is idempotent (`ls-remote`) and pushes a plain fast-forward with batch ssh and
  bounded network verbs.
- Refusals are `not_on_target`, `non_fast_forward` and `push_failed`, each with an item note. Transport failures are
  retried.
- The landed check runs at all six readiness sites. Close-out has an `## Integration` table.
- Migration `0039_integration`; cache `0013_integration`.

## Milestone 2 - Settings, visibility and retry (`56c0e5cb..4665aba2`)

- **Settings.** The project default is the project-only registry key `integrate` (Settings > Prompt). The repo
  mode is a choice row of the Hierarchy repo editor. Both refuse `pull_request` and a non-`local` mode without a
  remote (`IntegrateMode::selectable_refusal`).
- **Display states.** `landing` (`⇡`) and `landing refused` (`↯`) are derived from the latest graph run's records
  (`RunLanding`, `ItemState::of_landing`) on Pg, Mem and the cache. `is_finished` is `done | landing | landing
  refused`; the close-out law is MOD-135's.
- **Retry.** A refused record is a `landing` waiting row, and `Unblock` retries it (`UnblockCase::RetryLanding`,
  `WriteStore::retry_landing`).
- **Review fix round R1** fixed a sweep/Unblock double push and `Q` on a landing item. No migration.
- Commit `a4a22aa3` alone does not compile `htui`; the next commit does.

## Milestone 3 - the `pull_request` run branch (`df7314ab..30ad4529`)

Design (plan D1-D8, from a code-architect blueprint). There is no migration and no cache change.

- **Run branch (D1).** `Isolator::run_branches` makes sure `refs/heads/htui/item/<key>` exists, under the repo's
  admin lock. It creates the branch at `HEAD`, fast-forwards it when it is behind, keeps it when it has diverged
  (maintainer decision 2026-11-15: an earlier run's branch is **reused**, so a re-run updates the same PR), and
  refuses `run_branch_checked_out` when any worktree has it checked out (or is rebasing or bisecting it). It runs
  lazily whenever a step base is computed, so a resume simply ensures again.
  - The name is frozen as `IntegrateSnapshot.run_branch`, built by `run_branch_name`. Two projects sharing one
    checkout with equal keys would share a branch; this is accepted.
- **Step base (D2).** `Engine::run_branch_base` lays the run-branch tips over `isolator.base` as a width-1
  `FanoutSlot` for walked steps, fan-out groups (`group_base`) and divided parts (`base_refs`, so the integrate step
  too). `local`/`push` runs make no extra isolator call, so their call logs are byte-identical.
- **Reconcile onto the branch (D3).** `Isolator::reconcile_onto` (with `reconcile` as a provided method) merges
  each winner into a detached, locked landing worktree `<scratch>/<run>/landing/<repo>`.
  - It keeps reconcile's discipline: the admin lock, D136 `merge_of` recovery, `merge --no-ff`, abort on conflict
    and the `merge_conflict` park.
  - The ref moves with a gix compare-and-swap (`git::move_branch`, `MustExistAndMatch`). A checked-out branch is
    re-checked right before the move.
  - A landing tree left mid-merge or dirty is reset; a reset that fails refuses `dirty_landing_tree`.
  - Cleanup removes the landing tree, even one whose directory has vanished, and keeps the branch.
- **Snapshot (D4).** `frozen_integrate` freezes the run branch and refuses `pull_request` when any phase isolates
  `local` or `shared_serialized` (`integrate_pull_request_in_place` names the phase), or when the item key is not a
  branch name. The M1 refusal `integrate_pull_request` is gone.
- **The record after the push (D5).** A new `LandOutcome::Pushed { hash }` keeps the record `pending` with
  `landed_hash` set.
  - `take_integrations` skips such a `pull_request` record, so sweeps leave it to MOD-134. Mem and Pg agree; the
    `.sqlx` cache was regenerated.
  - It is not landed, so dependents wait, and the item reads `⇡ landing`.
  - An empty run branch (already on the local target) is `Landed` with nothing pushed.
  - A run branch that moved on the remote refuses `non_fast_forward`.
  - A `pull_request` record whose snapshot names no run branch is refused (`no_run_branch`), so it surfaces in
    Unblock.
- **Close-out (D6).** A pushed `pull_request` row reads
  `` pushed `htui/item/<key>` at <short>; pull request not opened (MOD-134) ``. `push`/`local` bytes are unchanged.
- **Settings (D7).** Unchanged; `pull_request` stays unselectable until MOD-134.
- **Tests.**
  - Store: five conformance cases (store `CASES` 349 → 354).
  - Real git: `gix_isolator` cases for cut, reuse, fast-forward, diverged, the checked-out refusal, conflict,
    D136, the CAS mismatch, the mid-merge reset, cleanup, and push once, never forced.
  - Engine (FakeIsolator): `landing` cases, including a `push` run's unchanged call log.
  - End to end: `tests/it/run_branch.rs`, a two-phase `worktree` run over real git against a bare remote. It checks
    that the primary is unmoved, the second step bases on the first merge, the branch is pushed, and the record is
    pending with its hash.
- **Review gate (`rust-reviewer`)** found one high and six lower findings, all fixed in R1 (`17140fa7..30ad4529`).
  - High: the reconcile ref move did not re-check a checked-out run branch.
  - The others: a mid-merge landing tree refused forever, untested CAS and step-base paths, cleanup of a vanished
    landing tree, `checked_out_at` missing rebases, a silent no-run-branch record, and two private rustdoc links
    that turned the gate red.
