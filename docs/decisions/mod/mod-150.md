  - Without that link, the close-out writes one, in its own transaction, from the item the person
    names (`close_out(…, names: Option<ItemId>, …)`).
  - It is refused with neither (`close_out_needs_a_link`, `close_out_names_no_link`).
  - The Runs pane asks "duplicate of which item?" only when no link stands.
- **M3, links to documents** (2026-11-14, `a74eaf51..eed26b32`, plan

  - A new table `item_artifact_link` (migration `0034_item_artifact_link`, mirrored by cache
    `0011_item_artifact_link`) links an item to one document version, with kind `origin`, `relates` or
    `implements`.
  - MCP `item_link` takes `to_document: {owner, kind, version?}`. No version pins the latest at write,
    and the reply names `version` and `latest`.
  - The Graph tab draws each linked document as a leaf row under the item that links it:
    `→ implements ANA-35 verdict v2 (latest v4)`.

## Decisions

- **Kinds and rules (M1).**
  - **One `parent` and one `duplicates` per item, never a parent cycle, depth at most 8.** On Pg,
    `parent` writes take one database-wide advisory lock (`item_link:parent`). `duplicates` takes a lock
    per item: review R1 found that the partial unique alone turns an idempotent upsert into a 23505
    under a race.
  - **A tombstone revival runs every check an insert does.**
  - **Graph word:** `duplicates` reads "duplicates", not ANA-35's "duplicate of", so the kind column
    stays 10 cells wide.
  - **Agents propose the three kinds live**, as `blocked_by` is today. MOD-155 adds the pending state
    with no API change.
- **Close-out (M2).**
  - The rule runs after the close-out law and before any write.
  - **Pg:** the `duplicates` advisory lock comes first. The standing link row is held `FOR SHARE`, so a
    concurrent withdraw waits. The two item rows are locked in id order (review M1, L1; both races are
    pinned in `pg_criteria`).
  - The Runs pane is the only close-out surface (PRD open question 3).
- **Documents (M3).**
  - **A version is a `document` row.** `item_artifact_link.to_document_id` pins one row, and "latest"
    is `MAX(version)` per (project, `item_id` not distinct, kind). An item's document and an owner
    document of the same kind never mix.
  - **`to_attachment_id` is a bare `UUID` with no foreign key and no writer.** MOD-114 (3) adds the
    `attachment` table and the FK.
  - **How the owner is read:** as an item key first (bare, `slug:KEY` or `@ws:KEY`), then as a project
    slug (a workspace by its scope row, `@ws`).
  - **Order (review M1):** the owner is resolved and its reach checked **before** the kind and version.
    An unknown owner and an unreachable one both read `document_outside_reach`, so an agent cannot
    probe what exists outside its reach. On `remove`, an existing owner with no live link reads
    `not found: item_artifact_link`, as `withdraw_link` checks no reach (MOD-147 edge 9).
  - **One pinned version per (item, link kind, document).** Linking a second version is refused
    (`document_already_pinned`) until the first is withdrawn. That keeps `remove` unambiguous without
    a version, and keeps the Graph to one row per document. On Pg it is serialised by a per-item
    advisory lock (`item_artifact_link:<from>`); `pg_criteria` races two versions.
  - **The `links()` read** fills `LinkGraph.documents` (`#[serde(default)]`) for every reached item.
    Documents are leaves: the walk never continues through them.
  - **Delete reach:** `DeleteReach.document_links` counts links whose item or document is in the
    deleted project, tombstones included.
  - **Indexes (review L4):** the document index is not partial, and `proposed_by_step_id` has its own
    index for the `SET NULL` cascade.
