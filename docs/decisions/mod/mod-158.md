## What was built

- **The URL is one database-wide setting.** It is the `app_setting` row `qdrant_url` (D1), stored as a JSON
  string, with no migration. Every write is a compare-and-set on `updated_at`: a stale token writes nothing and
  answers `Stale(None | Some(current))`. A malformed row stays readable with its token, so it can be overwritten
  or cleared (P-3). On Postgres the four statements are the existing `app_setting` ones, reused byte for byte,
  so `.sqlx` is unchanged. MemStore's token always moves forward, even under a frozen test clock.
- **`QdrantUrl` (`htui-core/src/qdrant.rs`) is the one validation** (D2, P-20, R1 H2). It accepts `http` or
  `https`, a host and an optional port 1-65535, and refuses:
  - userinfo (an `@` anywhere), a query or a fragment (`R-STO-1`: no credentials in the URL);
  - anything outside printable ASCII;
  - host characters outside letters, digits, `-._~` and `%XX`;
  - a bracketed host that is not an IPv6 literal.

  No refusal echoes the input. Settings, the CLI and the env override all show `QdrantUrlError`'s own
  sentences, and `QdrantSettings` can only be built from a `QdrantUrl`.
- **Resolution, one function** (`concepts_worker::resolve_settings`, D3/D4):
  - **URL:** `HTUI_QDRANT_URL` (development/CI override, per process; an invalid one is an error and never
    falls back to the row), otherwise the `qdrant_url` row, otherwise "no Qdrant URL".
  - **Key:** `HTUI_QDRANT_API_KEY`, otherwise the OS keyring. A headless worker reads `--qdrant-key-stdin`
    (the line after the DSN), otherwise the keyring, otherwise the systemd credential
    `$CREDENTIALS_DIRECTORY/htui-qdrant-key`. No key anywhere is allowed.
  - No test reads `HTUI_QDRANT_*` from the process (P-13): `QdrantEnv::from_process()` is called only from
    production entry points.
- **Picked up live** (D6, P-2): the store worker publishes its `PgStore` to the process-wide index at the top
  of every loop iteration; a changed pool after `SetDsn`, going offline or going online is published, and an
  unchanged one is skipped. `htui worker` publishes its pool after connecting. Every search and every index
  cycle resolves again, and the connection cache reconnects when the URL or key changed. It drops a connection
  after a failed sync and clears itself when settings stop resolving.
- **The worker's index job** always starts and resolves per cycle (D7). With no URL it logs one line and
  sleeps; a URL set later is indexed on the next cycle with no restart. `search_concepts` is offered on a
  worker when a URL resolves at worker start (Q3); MOD-160 moves that check to session start.
- **Nothing of htui's own reaches a child process** (D5, `R-SEC-2`). `htui_core::secret::HTUI_OWN_ENV`
  (`HTUI_QDRANT_API_KEY`) is removed at every place htui starts a process: agent launch (after
  `.envs(&launch.env)`), both step shells, git verbs and the git version probe, the browser opener, `$EDITOR`,
  and provision's `ssh` (the last two added as R1 hardening H1). The URL holds no secret and stays visible.
- **Settings > Qdrant** (D9, D10):
  - **Rows:** the URL row edits the database setting and says it applies to every box; any override in force
    is shown under it. The API key row stays this box's keyring entry.
  - **Writes:** each write carries the snapshot's token; a stale write says "changed elsewhere" and re-reads.
    `c` clears only the focused row, after that row's own question (Q2). After any failed write the section
    reads itself again.
  - **Old keyring URL** (the retired per-box `qdrant-url`), shown on its own row: `u` (`Act::QdrantAdopt`,
    rebindable in `keys.toml`) inserts it expecting no row, then removes the keyring entry. It can also be
    discarded; it can only be discarded when a row already exists or the old value is not a usable URL.
  - **Launch check:** a narrow request reads only the old keyring entry, off the store loop. If one is there,
    the status line says so once per launch, without clobbering an earlier notice.
  - **Offline and demo:** offline, the URL row "cannot be read while Postgres is offline"; `--demo` shows
    n/a.
- **CLI** (D8): `--set-qdrant-url <URL>`, `--clear-qdrant-url`, `--set-qdrant-key` (one line of stdin into
  this box's keyring) and `--clear-qdrant-key`. Exits are those of `StateExit`: 2 refused, 3 offline,
  1 failed. `--search-items` and `--index-items` now refuse in this order: DSN, connect, URL (the URL lives in
  Postgres). See `docs/htui-cli.md`.
- **`htui provision`** (D11, Q1): when this box's keyring holds a key, provision encrypts it as
  `htui-qdrant-key` beside `htui-dsn`, sending it on INSTALL's stdin only, and adds its
  `LoadCredentialEncrypted=` line to the unit.
  - A host whose `sh` has no `printf` builtin is refused when a key would be sent.
  - A key holding a control character is refused before any remote call.
  - A keyless re-run keeps an existing host key line. `--replace-credential` re-encrypts the key and restarts
    the unit.
  - A credential changed by hand needs `systemctl restart htui-worker`, because systemd decrypts it only at
    unit start (`docs/htui-worker.md`).
- **Sandbox** (D12, P-1): `docker/hr/compose.hr.yaml` sets `HTUI_QDRANT_URL` to the run's own Qdrant, so a
  sandbox never reads the database row for another Qdrant (`tests/hr/hr.bats` `3h2`).

## Decisions at the gates

- **Routing:** plan, by maintainer override; ultracode for the implement phase; MOD-160 kept separate.
- **CONFIRM:** Q1 provision includes the key credential; Q2 `c` clears the focused row; Q3 the worker's
  `search_concepts` gate is checked at worker start. All three as recommended.
- **Review gate:** `rust-reviewer`, run as three area instances.
  - Verdicts: area A approve, area B approve with fixes, area C approve with fixes. Nothing critical or high.
  - The maintainer chose all three mediums, all cheap lows and both optional hardenings (H1: strip `$EDITOR`
    and `ssh` too; H2: strict host characters). All were applied in R1.
  - R1's verify rounds caught two regressions in the fixes, both repaired:
    - MemStore's token reused after a clear and a fresh insert;
    - a doc sentence claiming `--replace-credential` needs a manual restart.

## Deviations from the plan (recorded in the blueprint)

- **D12's file:** the override lives in `compose.hr.yaml`, not `scripts/hr` (P-1).
- **Publishing:** the store worker publishes every iteration, not only on `go_online` (P-2).
- **`StoredQdrantUrl.url` is a `Result`** (P-3).
- **The notice and harnesses** (P-6): the status-line notice is gated by `register_all`, so harnesses never
  read the real keyring.
- **`testkit.rs`** gained a test-only hook that hands a `QdrantEnv` into the harness, so Settings reads under
  an injected environment. That is P-13 taking precedence over P-16, judged sound by the review.

## Not verified here

- **Live-Qdrant tests:** `htui-store` `qdrant_live`, `htui` `qdrant_worker` and `state_cli_pg`'s index case
  fail in this sandbox.
  - The failure is `create collection: ... Timeout expired`: the run's Qdrant takes about 3.5 s to create a
    collection, and the client gives up at about 5 s.
  - The same failure occurs on the tree without MOD-158, and at idle. Suspect the run-dir Qdrant storage bind
    of `0dc8c51f`.
  - **Owed on the host**, together with `bats tests/hr/hr.bats -f 3h2` (no bats or docker in the sandbox) and a
    real `htui provision` against a host holding a key.
