- **Keys stored, by owner.** Migration `0034_requirement_keys` turns `requirement.key` from a generated column
  into a stored, `NOT NULL` one (values kept), re-letters any key in a workspace scope row `W-`, and adds
  `refines_id` (`ON DELETE SET NULL`), `child_number`, a nullable `number`, the CHECKs
  `chk_requirement_number_or_child`, `chk_requirement_child_refines`, `chk_requirement_key_shape`
  (`^[RW]-[A-Z][A-Z0-9]*-[1-9][0-9]*(\.[1-9][0-9]*)*$`), the uniques `uq_requirement_key (project_id, key)` and
  `uq_requirement_child (refines_id, child_number)`, and the table `requirement_child_counter` (one row per
  parent). A mint in a scope row is `W-<AREA>-<N>`, in a project `R-<AREA>-<N>`.
- **Nesting and refinement.** `NewRequirement.refines_id` (the `mint_requirement` signature is unchanged). Same
  owner: a nested child in the parent's area, keyed parent plus `.<child_number>` from the per-parent counter,
  `number` NULL; the area counter does not move. Cross owner (a project requirement refining one of its
  workspaces'): a top-level key from the child's own area. A workspace requirement may refine only its own
  workspace's (so it nests). Refusals, in order and before any counter moves: unknown area, unknown parent
  (`NotFound { entity: "requirement" }`), outside reach (`requirement_refines_outside_reach`), a nested child asked
  in another area (`requirement_child_area`), a withdrawn parent (`requirement_withdrawn`). Pg mints in one
  transaction and reads the parent `FOR SHARE`, so a concurrent withdraw cannot slip in; eight concurrent nested
  mints take `.1`..`.8` (`pg_criteria`).
- **Order.** Lists sort by area code, then the numeric key path, then the key (`R-ENT-1 < R-ENT-1.1 < R-ENT-1.2 <
  R-ENT-2`, `.10` after `.9`): `Requirement::list_cmp` (allocation-free) in Mem and the mirror, an `int[]` key
  path in Pg's `ORDER BY`. New read `ReadStore::requirement_refinements(id)`.
- **Coverage.** `CoverageState` (`Open`/`InProgress`/`Covered`) and `htui_core::store::requirement_coverage_state`.
  A requirement with live refiners follows them: covered when all are, in progress when any is covered or in
  progress, open otherwise, recursively (`W-ORCH-3 → W-ORCH-3.1 → R-API-4`); withdrawn refiners are ignored, and a
  requirement whose refiners are all withdrawn falls back to its own citations. Leaf rule: covered by a live,
  non-suspect `addresses` citation from an item closed `done`/`concluded`; in progress by a live `addresses` from
  an open or blocked item, or a suspect done one; an `addresses` from an item closed any other way (`rejected`,
  `duplicate`, …) counts as nothing; `reserves` never counts (`verifies` should once MOD-114 adds it). Offline,
  the mirror holds only mirrored projects' refinements, so the result is not authoritative there (documented on
  the function).
- **Mirror and delete.** Cache `0011_requirement_keys` recreates `requirement` with the new columns; the child
  counter is not mirrored. `DeleteReach.requirement_child_counters` counts the cascading rows, and the TUI's
  delete warning names them. Deleting a workspace detaches member requirements that refined its `W-` ones (they
  keep their keys); deleting a lone parent that still has a nested child is refused by the CHECK (`23514`).
- Store conformance `CASES` 312 → 319 (seven cases: W- mint, nested keys, cross-owner key, refusals outside
  reach, refinement lists, coverage from splits with recursion and withdrawn refiners, workspace delete);
  Postgres `TABLES` 54 → 55; migration pins 33 → 34.
