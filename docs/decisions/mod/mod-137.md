## The problem

A step graph's topology was implied: phases ran in `position` order, and the review loop's target came
from a name rule in `gate::loop_target`. Graphs could belong only to a project, and an edit was a series
of per-row writes each CAS'd on its own `updated_at`, with no deleter, so a graph could not be edited
atomically and an item's override could not be re-cloned (`graph.rs`'s "Re-override is still owed").

## What was built

- **Migration `0020_step_graph_v2.sql`** (ANA-33 said `0019`; MOD-125 took it):
  - `step_graph_edge` (`next`, `if`, `asks_you`, `changes_requested`, `fails`; `predicate` JSONB only on
    `if`; `loop_limit`, required on `changes_requested` and `fails`). Its endpoints reference
    `step_graph_phase(graph_id, id)`, so an edge cannot leave its graph and goes with its phases.
    `loop_limit`, not `limit`: `limit` is reserved in Postgres.
  - Owner scope: `step_graph.workspace_id`, a nullable `project_id`, at most one set (neither is the
    global library), one partial unique name index per scope, and overrides only in a project.
  - `step_graph.revision`, the whole-graph CAS token.
  - Node columns `split` (backfilled `compete` where `fan_out > 1`, and kept in step with it by
    `ck_phase_split_fan_out`), `palette`, `plan_scope`, the divide planner and integrate persona, agent
    and model columns, `max_parts`; table `phase_part` for a divided node's default parts.
  - The position and name uniques re-created `DEFERRABLE INITIALLY IMMEDIATE`, so one transaction can
    swap them.
  - The backfill: `next` between consecutive positions and, per `review`, a `changes_requested` edge to
    the greatest earlier `implement`, else the previous phase in position order, with the target's
    `retry_limit` as `loop_limit`. The rule is `seed::default_edges` in Rust too; a migration test pins
    the two equal on every seeded graph (`bug` is the one fallback, `review -> fix`).
- **Model:** `GraphScope` (`Project`/`Workspace`/`Library`) on `StepGraph` and `NewStepGraph`,
  `revision`, the node fields, `StepGraphEdge`, `EdgeKind`, `EdgePredicate`, `PhasePart`, `GraphBody`,
  `NodeBody`, `Split::for_fan_out`.
- **`WriteStore`** on MemStore, PgStore, `Writer` and both test spies: `replace_graph` (nodes diffed by
  phase id so a kept node keeps its bindings; candidates, parts and edges replaced whole; CAS on
  `revision`), `delete_phase`, `delete_edge`, `delete_phase_agents`, `graph_edges`, `phase_parts`,
  `graph_body`. Every content write bumps `revision`, Postgres as the first statement of its
  transaction so the graph row is locked before any phase row. Both stores decide every refusal before
  writing, in one documented order and one wording, through shared pure rules
  (`store/graph_rules.rs`). Seeders and the demo write edges. `delete_workspace` takes its graphs;
  `delete_persona` counts the divide and part personas.
- **Catalogue:** `StoreRequest::ReplaceGraph` and `DeletePhase` on `catalogue::serve` (stale answers
  `CatalogueStale`); a `GraphEntry` is the graph's whole `GraphBody`, one `graph_body` read per graph.
  No editor UI (MOD-141).
- **Overrides:** the first override copies edges, remapped, through one `replace_graph`; a second
  override re-clones from the kind's default graph into the same graph (ANA-2 `:317-320`, D13); a
  failed first override's orphan is adopted by the next call.
- **Not built (by decision D4):** runs and items still use only their project's graphs, and nothing
  reads edges at run time. Both are MOD-138's (snapshot v2, the walker, the shared validator).

## Review

`rust-reviewer` ran as three area instances (Postgres and migration; core and MemStore; orchestrator
and catalogue): approve with fixes, no critical or high findings. Round R1 fixed all four medium
findings and the lows, in two lanes, each verified by read-only lenses:
- a Postgres deleter or `update_phase` racing a concurrent delete answered `Ok` or the wrong
  `NotFound` (existence is now decided by a statement after the bump);
- a failed first override blocked every retry (body pre-checked before any write; orphan adoption);
- `GraphEntry` could not seed a lossless `ReplaceGraph` (it is now the whole body);
- the refusal-order case did not order the store-specific steps (now pinned end to end).

The verifiers also found the deferrable uniques' trigger order (FK checks fire before a deferrable
unique), which T2 answered with a clash pre-read.

**Stack:** the workspace gate (only the workspace build, never the per-crate one) overflowed
`pg_store_conformance` at the 2 MiB debug test stack, twice. Measured with `RUST_MIN_STACK`, the
pre-MOD-137 tree already failed at 1.75 MiB. Every `run_case` arm, the match, and `PgStore::replace_graph`'s
nested writers and reads are now boxed; the suite passes at 1.5 MiB.

**Accepted, for the record:** a re-override copies the kind's default graph even when the first
override cloned another project graph (D13). Pre-existing rustdoc errors in htui-store are unchanged.
