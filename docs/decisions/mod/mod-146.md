## What was built

- **`project_type`** (Postgres migration `0020_project_type.sql`): ANA-35's P3 columns (`slug`
  primary key with a slug CHECK, `name`, `description`, `coding`, `builtin`, `selectable`, `seed`
  JSONB, `seed_version`, `created_by`, both stamps), named constraints (`chk_project_type_slug`,
  `chk_project_type_seed`, `fk_project_type`) and an `updated_at` trigger. Six built-in rows, no
  recipes: `docs`, `general`, `ops`, `research`, `software` (the only `coding` type), `workspace`
  (the only one not `selectable`). `project.type TEXT NOT NULL DEFAULT 'software' REFERENCES
  project_type(slug)`, so every existing project is `software`.
- **Model:** `ProjectType` in `htui-core`; `Project.project_type` (SQL `type`, a Rust keyword). The
  built-ins are `seed::PROJECT_TYPES` and `seed::DEFAULT_PROJECT_TYPE`. MemStore answers from that
  constant; a Postgres test pins the migrated rows equal to it.
- **Read:** `WriteStore::project_types`, beside `personas()`, on every implementor (MemStore,
  PgStore, `Writer`, the two test spies), ordered by slug bytes on both stores. This is the read
  ANA-39 and MOD-128 use for `coding`. Two conformance cases cover both stores.
- **Mirror:** `cache_migrations/0007_project_type.sql` adds the `type` column only. The table is not
  mirrored, as `persona` is not, so offline Settings says the list is unavailable.
- **Settings › Project types:** a read-only, app-wide section appended after Queue, one line per
  type with its description beneath. Keys go through `keys.toml` (`settings.project_types`), and j/k
  are the shared list acts.
- **The Settings strip scrolls** (maintainer decision on blueprint F-1): with eleven sections the
  strip is 102 columns wide, past `the_section_strip_width_is_pinned`'s 100-column frame. It now
  scrolls so the active title stays whole, opening on a dim `…` when scrolled. When it fits, it draws
  as before.
