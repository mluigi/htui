## PRD gate (maintainer, 2026-11-15)

- **Q1 - coordinator chats wait for MOD-136/MOD-121.** The new-workspace and new-project forms create no chat; no
  coordinator chat existed in code.
- **Q2 - a plain folder is refused until MOD-145.** "Existing folder" must open as a git repository; the refusal
  names MOD-145. Git URL and new repo ship in full.
- **Q3 - the workspace row leaves Settings › Hierarchy.** Creating, editing, the folder and deleting a workspace
  are the Workspaces tab's. Hierarchy keeps the open workspace's projects, repos and documents until MOD-123.
- **Q4 - an idle workspace reads `○ stopped`, with no stop row written.** So runs can start there without a resume.
- **M3 OQ1 - no clone cancel.** A clone is bounded instead (10 minutes, never prompts); `Esc` closes the form and
  the clone finishes in the background.

## What the maintainer can do now

- **See every workspace.** Workspaces is tab 1 (every other tab's digit moved up by one); `w` jumps to it. Each
  workspace reads `● open`, `◐ background · n running`, `◌ stopping…` or `○ stopped` (`· n held` when a stop holds
  runs). Under each are its overview and its projects. The overview shows the state, the folder on this box, the
  description, the goals document, the projects with item counts, running and waiting, the default target and a
  Runs section. Status is always a glyph plus a word.
- **Open one without stopping another.** `o` opens a workspace. The one left keeps walking its runs (the executor
  was already box-scoped; a test pins it). The header shows `+N in background ◐ n`. The last open workspace is
  remembered in `ui-state.toml` (not under `--demo`).
- **Stop and resume from the tab.** `s` stops gracefully, `s` again forces, `r` resumes. Each asks first and lists
  every run with what will happen to it, in the same words as `htui stop`. A stop that someone else changed while
  the question was open is refused and the box says so. The open workspace can be stopped too
  (`● open · … · stopping…`).
- **Leave safely.** The leave dialog lists every live workspace. `S` stops them all gracefully, waits up to 20 s,
  then leaves. `Enter` or a second `ctrl-c` leaves at once.
- **Create and edit.** `N` offers a workspace or a project. The workspace form's folder follows the name until
  edited, shows a preview, and creates the folder. The project form takes an existing git folder, a git URL (cloned
  into `<workspace folder>/projects/<slug>`) or a new repository (`git init` plus one empty commit, nothing else in
  its tree). `e` edits a workspace (a slug change never moves its folder), `d` deletes it (count, warning, typed
  slug), and `T` sets its default target.
- **Old key files keep loading.** A `[switcher]` table or a `[settings.hierarchy] new_workspace` entry loads with
  one notice.

## M1 - the tab, states and opening (2026-11-15)

Commits `01cdb979`..`db97562a`; review fix round R1 `dc559952`..`f8037cd8`; phase note `5457063c`.

- **No new column and no migration.** `WorkspaceLifecycle::of(open, counts)` in `htui-core/src/model/stop.rs`
  derives every state from three things: the TUI's scope, the runs, and MOD-125's `workspace_stop` row. ANA-35 §9.
- **One store read for every workspace.** `WriteStore::workspace_run_counts()` answers in one call (Postgres: one
  query served by `idx_run_workspace_status`; `EXPLAIN` with 200,000 done runs took 0.75 ms). It is on every
  implementor. Store conformance `CASES` went from 343 to 344.
- **Two new requests.** `WorkspaceRunCounts` runs on the shell's once-a-second refresh. `WorkspaceOverview` is
  served by `crates/htui/src/workspaces.rs`, which mirrors Hierarchy's snapshot.
- **The switcher overlay is deleted.** `[workspaces]` took its key slots, so no other key position moved.
- **R1 (two reviewer instances, 4 medium and 5 low findings), what changed:**
  - `w` lands on the open workspace after a restart.
  - The overview is re-read when the tab is activated, and a refused read is retried.
  - Startup no longer rewrites a `ui-state.toml` that failed to load.
  - Offline, the tab shows no stale states and no background chip.
  - The tests deleted with the switcher got replacements.

## M2 - stop, resume and leaving (2026-11-15)

Commits `266f3896`..`1692b8bb`; review fix round R1 `a3305744`..`5c8926a3`; phase note `47e4ffa6`.

- **One shared report module.** `crates/htui/src/stop_report.rs` holds `htui stop`'s report, its wording and the
  race-checked writes `write_stop`/`write_resume`. The CLI's output is byte-identical, pinned by its untouched tests
  and `report_stopping.snap`. The CLI reads no step rows (R1 F4).
- **Two new requests.** `StopWorkspaces` (batched, for the leave dialog) and `ResumeWorkspace`.
- **The tab's keys.** `s`, `s` again and `r` each ask a question built from a fresh overview read. Stop and resume
  hints follow the state.
- **The leave dialog keeps state.** It lists every live workspace and has `S` (`leave.stop`). Its text still
  promises nothing about work surviving a leave (MOD-115 MD6; MOD-125 Q5: TUI shutdown stays a hard drop).
- **R1 (1 reviewer, 3 medium and 5 low findings), what changed:**
  - A batch that fails partway reports every target.
  - Offline, the leave dialog lists no other workspaces and offers no `S`.
  - A target stopped meanwhile by someone else is waited for.
  - The settle bound is measured in wall time.
  - The dialog's own counts refusal stays off the status line.

## M3 - creating and editing (2026-11-16)

Commits `133d6b4e`..`30f4fb69`; review fix rounds R1a `604a1244`..`bbe85787` (git and the worker) and R1b
`be6726d0`..`e7840b36` (the tab, Hierarchy and the docs).

- **Git helpers in `htui_orch::isolate::git`.**
  - **Clone:** `Cli::clone_repo` runs `-c protocol.ext.allow=never` with `--` before the URL, a 10-minute budget,
    `GIT_ALLOW_PROTOCOL` pinned, credentials redacted, and no askpass program ever called (`GIT_ASKPASS=""` in
    `NETWORK_ENV`, so ls-remote and push are covered too).
  - **New repository:** `Cli::init_with_empty_commit` makes one commit with htui's identity, with
    `core.hooksPath=/dev/null` and no signing.
  - **Repository checks:** `repo_facts` (which reports the work tree) and `enclosing_repository`.
- **The worker side, in `crates/htui/src/workspace_setup.rs`.** It serves five requests: new workspace, edit
  workspace, new project, target choices and set target. `NewProject` runs on its own task, and a panic in it is
  still answered.
  - Disk work happens before any row is written. A failure removes only what this request made, deciding that from
    its own `mkdir` of the leaf.
  - A typed `..` is refused.
  - A workspace folder inside any repository's work tree is refused (`R-ID-4`).
  - A failed store write after a create or an edit is undone.
- **The tab.**
  - `N` opens a chooser and the two forms. A form's hints sit on its own pane. A local URL expands `~` and a
    relative one is refused.
  - `e`, `d` and `T` work as described above.
  - The once-a-second counts read now also runs for a workspace with no projects (D16, an M1 bug M3 would have made
    visible).
- **Hierarchy keeps only projects and repos.** Settings › Hierarchy's workspace row is read only, and its `e`/`b`/`d`
  notices name the tab's keys. `settings.hierarchy.new_workspace` is retired; `RETIRED_ACTIONS` loads it with a
  notice.
- **R1 (three reviewer instances, 6 medium findings, the rest low), what changed:**
  - No credential prompt.
  - No deletion of a pre-existing folder.
  - The `R-ID-4` check walks upward through parent folders.
  - The project form's source key is visible.
  - The taken-slug test asserts the store's words.
  - A test covers deleting the last workspace.
  - One verifier point was rejected with a pin test (`e7840b36`). It said a create's reply could close a second
    busy form, but the shell drops the superseded reply.

## Gate

The sandbox gate was run after each milestone's lane (M1, M2 and M3). Every step passed except `test`. In each run,
the only red test was `htui-store` `cache::the_spawned_refresher_passes_and_follows_the_scope`: M1 9141/9142, M2
9200/9201, M3 9290/9291. That is the known timing flake (5 s wait), in `cache/` code MOD-116 never touches. Run
alone during M1, it passed 5 of 6 times. Final gate after the M3 fix rounds (at `e7840b36`): every step green but `test`, 9314/9315, the same one red test; alone, 4 of 4 runs passed (6.5-33 s against its 5 s wait, load 5.8).

## Deferred and left open

- **The stop race check is check-then-act.** A stop replaced between the re-read and the write is still overwritten
  (M2 review L3). `htui stop` has always had the same window. Closing it needs a store-level conditional write.
- **Old worker requests stay.** `CreateWorkspace`, `UpdateWorkspace` and `SetWorkspaceRoot` are still served, but no
  screen sends them; MOD-123 removes them.
- **Not built here, by decision:**
  - coordinator chats (MOD-136/MOD-121);
  - plain-folder repos (MOD-145);
  - the components and requirements sub-tabs (MOD-117, MOD-118);
  - the memory sub-tab;
  - MOD-130's resolver wording on the target line (its M2).
