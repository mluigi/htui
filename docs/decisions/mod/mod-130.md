## What the maintainer can do now

Where a run runs is a record, not an assumption. A `target` names a kind (`local`, `docker`, `ssh`, `ssh_docker`,
`enrolled`), a locator of names and addresses (never values) and the box it is bound to. An item's target comes from
the first level that sets one: the item, its workflow, its project, its workspace, then the Settings default, and
the seeded `this box` target when none does. The run records the target and the level that chose it when it is
queued, and a later change to the cascade moves no queued or running run. Only `local` runs in this build: any other
kind, a retired target, a target bound to another box and a target that is not `ready` are refused at run start with
a sentence naming the level that chose it. A refusal other than a retired target also blocks the item with a note.

A driven target (a container on this box, an ssh machine) starts on this box. The queue, the claim and the worker poll
key on the box that **drives** the run, `COALESCE(executing_box_id, target_box_id)`, while tags and agent candidates
are checked against the box the work runs on. Only the `enrolled` kind waits for its own worker. A local run is
unchanged column for column.

It shows:
- **Runs tab.** Under a run's `kind status box started` and `mode finished` lines:
  `runs on docker-here · from project`. A plain local run on the default, a chat run and a run queued before M2 show
  nothing extra, so no existing snapshot of them moved.
- **Queue overlay.** `queued for <box>` and `running on <box>` name the box that drives the run, not the one its
  work runs on (pinned by tests; the wording itself was already right after M3).
- **Settings › Boxes.** A container box is listed under its machine (`└ docker-here`), and the detail pane gains
  `kind` for every box and `parent` for a container.

### M3 - The queue keys on the driver (`cf55f77f`..`d5030c43`, with R1 `9c53e272`)

driving box; `QueueRunFact` gains `driver_box_id`/`driver_hostname`). `NewRun.executing_box_id` and `driver_of`:

box `FOR SHARE` after the claiming box when the two differ. Handed to MOD-44 (maintainer Q2): the pre-enqueue tag
filters (`ready_items`, `missing_tags`, `missing_tags_of`, the Backlog) stay on this box until a container run can
start. No migration; `CASES` 350.

## Decisions and deviations worth keeping

- **No `EntryState` change (M4 P3).** The overlay already names the driver. A sentence naming both driver and
  target (`running on <driver> for <target>`) would move `EntryState::Elsewhere`, its `Display`, `sentence`, the
  queue overview and `htui state`; not done.
- **`kind` row on every machine.** The plan said both "a snapshot with no child reads byte-for-byte as today" and
  "`kind` for both kinds"; the second won (reviewer M1: judged correct). If a plain machine's `kind  machine` row
  is unwanted, showing it only for a container restores all seven snapshots.
- **Target line hidden for a plain local run (P1).** A level that pins the local target still shows
  `runs on this box · from project`.
- **Review (`rust-reviewer`, once).** Approved, no high findings. One medium (the seven snapshots, above) and
  low notes left as they are: a container whose parent is another container shows its parent's hostname rather than
  `(not listed)`; the clipping tests are ASCII only; the offline cache test has no retired-target case and returns
  early without a database.
- **Tags and Backlog filters stay on this box** until MOD-44 makes a non-local kind runnable (M3 Q2).
