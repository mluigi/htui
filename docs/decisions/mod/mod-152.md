Agents gain four MCP tools next to `command_run`, which stays the blocking form with its answer and
`BUSY` text unchanged:

- `command_start` queues a command and answers its `command_run_id` at once; a session-owned task runs
  it over the same `command_run` row, under the same class limits, lease reads and scrub.
- `command_wait` takes an absolute RFC 3339 `deadline` (clamped to 300 s ahead), an optional per-line
  regex `pattern` and `after_line`, and returns on a terminal row, a matching line, or the deadline.
- `command_cancel` stops a command this session started (queued or running) and answers the settled
  status.
- `command_output_read` reads a command row of the caller's run by tail, line range, or regex with
  context, under a byte cap (default 16 KiB, max 64 KiB); a running command's complete lines are
  served live.

`command_run` and `command_start` take a `repo` argument naming one of the session's `extra_dirs` by its
final path component; `cwd` stays relative to the chosen base, with no `..`.

## Decisions

- **D1 A separate `command_log` table** (migration `0031_command_log`, one row per `command_run`,
  `ON DELETE CASCADE`), not a column: `CommandRun` and every `command_runs()` read stay unchanged and
  cheap. `command_run.output` stays the 64 KiB scrubbed tail. Not mirrored by the cache.
- **D2 Cap: the last 2 MiB** of the merged output (`COMMAND_LOG_CAP`), cut on a line boundary; a line
  longer than the cap is dropped whole rather than split (review F6). The store refuses text over
  `COMMAND_LOG_CAP + 4096` with `Constraint`, in both stores.
- **D3 Scrub fail closed, whole text first.** The stored log is scrubbed as one text; an unmaskable log
  is stored as `[log withheld: it matched credential rule <rule>]`. Live reads (`command_wait`,
  `command_output_read`) scrub the whole live text once and slice the scrubbed text (review F1 tightened
  the plan's "scrub the slice" wording, which let a PEM body or a secret split by a 4 KiB cut through).
  Patterns match scrubbed text only.
- **D4 Log before finish.** The runner stores the log, then finishes the row, so a waiter that sees a
  terminal row can read its log. The 2 MiB scrub runs on `spawn_blocking`, awaited before both writes.
- **D5 Two store methods**, unfenced like the queue's own writes (the session reads its lease before it
  queues and on every heartbeat): `put_command_log` (upsert; unknown row `NotFound`) and
  `command_log_of_run(run, id)` (the caller's run's rows only; `id: None` is the latest by `queued_at`),
  on `WriteStore` and `WorkerStore`, through MemStore, PgStore, `Writer` and the spies.
- **D6** `run_shell_with` streams every chunk to a sink; `run_shell` wraps it with a no-op sink.
- **D7 Lifetime.** At most 4 started commands queued or running per session. Each started command's
  stop token is a child of the session's cancel token: session end, a lost lease or `command_cancel`
  kills the process group and ends the row `cancelled`, with the reason as the log's last line
  (`[stopped: cancelled by command_cancel]`, `[stopped: the session ended]`). The registry keeps at most
  64 ended entries; `command_cancel` on a pruned id of this session answers from the store (review F4).
- **D8 Line numbers are absolute** (review F2): line 1 is the first line the command printed, live or
  stored. A cut log opens with `[… earlier output truncated] (lines 1-N)`, so `after_line` taken from
  a previous `next_line` never skips lines past 2 MiB.
- **D9 Approval posture (maintainer, at CONFIRM).** `command_start` and `command_cancel` join
  `ASKING_TOOLS`; `command_wait` and `command_output_read` run nothing and are pre-approved.
- **D10** All four tools are advertised exactly where `command_run` is (`scope.command_queue`);
  `COMMAND_QUEUE_TEXT` is untouched (MOD-151 owns the prompt digest change). `docs/htui-mcp.md`
  recommends `command_start` for long commands instead of raising the client timeout.
- **D11** `ToolScope.extra_dirs` is set by the engine from the isolator's list; chats pass none.

## Review

`rust-reviewer` (Opus) over `759ba674..776e490e`: approve with warnings, no critical or high. Two medium
(F1 scrub-then-slice in `command_wait`; F2 line numbers sliding past 2 MiB) and four low (F3
`command_output_read` read order; F4 registry never pruned; F5 2 MiB re-decoded and re-scrubbed every
200 ms, now cached by byte count and decoded outside the lock; F6 mid-line cut). All six fixed in one
round (`dbb2020c`, `ecb51a64`); the fix-round verifier found nothing. F3 is covered by reasoning (the
entry is marked ended only after the log is written and the row finished), not a deterministic test.
