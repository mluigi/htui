# MOD-170 - Waiting key qualifier: one read per refresh tick (done, 2026-11-11)
**Requirements:** `R-TUI-11` (the waiting list); efficiency only, no requirement text changes.
**Origin:** MOD-147 milestone 2 review (MOD-147 is still open; its M2 phase note in `HANDOFF.md` names
this item).

**What was done.** Run in the sandbox on `hr/MOD-170`. Routed as plan (C3 only: the item offered a
batched read or a cache); the maintainer accepted the route and the plan. Plan:
`.claude/plans/mod-170-waiting-qualifier-one-read.plan.md` (`837630de`, verified-claims table inside).

**The cost.** The top bar's `StoreRequest::Waiting` (once a second) built its `KeyQualifier` in
`store_worker.rs::waiting_reads` with `scope_project`, then a `project()` and an `item_kinds` read per
scope project, one after another: 2N+1 Postgres round trips a tick online. `htui waiting`/`status`
(`state_cmd.rs::answer_online`) paid the same per call.

## Decisions

- **D1: one batched read, not a cache.** Kind and hierarchy writes also come from other processes
  (the CLI, other boxes, the engine, MCP tools), which the store worker never sees, so a per-workspace
  cache would print stale keys until restart. Batched, the read is already one round trip.
- **D2: the scope row is folded into the query.** `PgStore::waiting_keys(workspace, ids)` selects
  `project` rows by `id = ANY($1) OR owner_workspace_id = $2`, flags the scope row
  (`COALESCE(owner_workspace_id = $2, false)`), and gathers each row's kind prefixes with
  `ARRAY(SELECT prefix … ORDER BY position, prefix COLLATE "C")`. `$2` is `NULL` when the caller does not
  widen. One query per tick, where the item asked for no more than one read.
- **D3: the store surface stays inherent.** `ScopeKeys` (`htui_store::ScopeKeys`), `PgStore::waiting_keys`
  and `Backend::waiting_keys` are inherent methods; no `htui-core` trait changed, so no conformance case
  or `CASES` count moved and no migration was needed. `Backend::waiting_keys` uses the query online; the
  mirror and memory are local and answer per project (scope row first, then the ids, each project once,
  a project not held left out), the same answer as the query.
- **D4: `waiting_reads` keeps its behaviour.** It widens with the answered scope row (`with_scope_row`)
  and builds the qualifier in `read.project_ids` order, leaving out a project the store does not hold, so
  its keys print bare; `StoreError::Unreachable` still propagates so `go_offline` fires. The htui-local
  `KindsRead` became `WaitingKeysRead` (implemented for `Backend` and the CLI's `PgStore`).
  Online, the qualifier now reads one consistent snapshot instead of several serial ones.

## Review (R1)

`rust-reviewer` found the behaviour and SQL equivalent to the old body in every edge case it checked
(no or unknown workspace, a scope row already in the scope, duplicate ids, an empty scope,
`widen = false`). Fixed in `71b884bd`: `cargo fmt` over the T1 code (High: the gate's first step failed),
and a parity case reaching the scope row both by id and through the workspace (Low: the mirror lists it
once only by its own dedup). Kept by decision (Low): `waiting_reads` clones each project's row out of the
answer per tick; that cost is negligible at workspace sizes and keeps duplicate ids behaving as before.

## Tests

`crates/htui-store/tests/cache.rs::the_mirror_answers_waiting_keys_like_postgres`: on Postgres, a
workspace ask flags and lists the scope row (`WS`) though not asked by id, lists each member with its
kinds in `item_kinds` order (both share `FEAT`), a project with no kinds with no prefixes, and leaves out
an unknown id; without a workspace nothing is flagged and the scope row is listed only when asked by id;
an empty ask answers nothing; the scope row reached both ways is listed once; and the offline mirror
answers each ask like Postgres. The existing pins on the qualified output stay green unchanged:
`store_worker.rs::serve_waiting_reads_the_demo_platform` (memory) and `tests/state_cli_pg.rs`'s waiting
cases (Postgres CLI path).
