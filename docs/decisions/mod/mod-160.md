# MOD-160 - Knowledge search fails open cheaply and says so (done, 2026-11-06)

**Requirements:** `R-NF-2`, `R-NF-3`, `R-STO-8`, `R-MCP-2`, `R-TUI-8`. No requirement edit: their text already
said this (ANA-37).
**Origin:** ANA-37 (`docs/ANA-37.md` §7.1, §7.4, §8 Q6; `docs/decisions/ana/ana-37.md`). Builds on MOD-158
(`resolve_settings`, the worker's start-time `search_concepts` gate, which this item replaces).
**Artifacts:** plan `.claude/plans/mod-160-knowledge-search-fail-open.plan.md` (D1-D10, Q1-Q4, verified-claims
table); blueprint `.claude/plans/mod-160-knowledge-search-fail-open.blueprint.md` (plan corrections P-1-P-14,
risks R-1-R-7). Routed **plan** (C4), ultracode for the implement phase, accepted by the maintainer. Sandbox run
`hr/MOD-160`.

## What was built

- **One sentence** (D1). `htui_core::qdrant::KNOWLEDGE_SEARCH_UNAVAILABLE` ("knowledge search unavailable") and
  `unavailable(cause)`. It covers no URL, an unusable URL, unreadable settings, an unreachable Qdrant, a refused
  key, an embedder mismatch and a model failure. It does not cover no collection (an empty index), no project
  in scope or an empty query.
- **The TUI and MCP search asks Qdrant first and never creates** (D2, D3).
  - `QdrantIndex::search` goes: settings, the cached connection, `ExistingCollection::find_in` (no collection
    answers empty: nothing created, cached or loaded), `ExistingCollection::check` (embedder and width, without
    the model), then the model, `open` and the search.
  - `sync` (Ctrl+R, the worker's index job, `--index-items`) keeps `QdrantStore::connect`, which creates by
    design.
  - Every Qdrant client is built in `vector.rs`'s `client_config`. It refuses a key that cannot be an HTTP
    header value before any client exists, because qdrant-client 1.19.0 echoes such a key in its error text.
- **Two connection slots** (D4). A cached connection is `Ensured` (made by `connect`) or `ReadOnly` (made by a
  search). A search takes either; a sync takes only `Ensured` and otherwise connects and replaces the slot.
- **`search_concepts` offered per session** (D5, Q1). `QdrantSource` caches "a URL is configured", refreshed
  off the loop:
  - after each publish of a changed store, each settings resolution, and each in-process URL write (the hook
    runs in the store loop, P-2);
  - by `offered()` itself, which starts one background re-read (single flight) when the value is over 30 s old.
  - `offered()` never awaits; unknown answers `false`. `ConceptSearch`/`ConceptIndex` gained `offered()`
    (default `true`), and `McpHost::open` reads it.
  - The worker's start-time gate is gone. The worker always attaches the production search and awaits one read
    at start, so its first session knows. A URL set later is offered without a restart (supersedes MOD-158 Q3).
- **Tool errors** (D6). `search_concepts` answers `isError` with `unavailable(cause)`, including the no-index
  case.
- **The concepts overlay** (D7, Q2). A failed search shows `knowledge search unavailable — <key> why`. The new
  `Act::ConceptsWhy` (`concepts.why`, default `ctrl-e`, rebindable in `keys.toml`) toggles a row with the cause
  and where to fix it. The Ctrl+R index line keeps its own error text.
- **CLI** (D8). `--search-items`' human line and JSON `error.message` carry the prefix; exit codes and
  `error.code`s are unchanged; `empty` stays `empty`; `--index-items` is unchanged.
- **Warnings that never block** (D9, Q4).
  - `htui_store::vector::probe` is model-free, bounded at 3 s, and answers `Ready`, `NoCollection`,
    `Unreachable`, `Refused` or `Mismatch`.
  - `concepts_worker::QdrantCheck` folds the probe and the settings into the states shown: **no Qdrant
    configured**; **unreachable or refusing the collection**; **the Qdrant refused this box's API key**;
    **this box lacks the key**; **this box cannot read the Qdrant settings** (R1, below). Plus an info line,
    not a warning: "this Qdrant answers without an API key".
  - `StoreRequest::ProbeQdrant` is served off the store loop by `ConceptsRuntime`, keyed by origin and kind.
  - **Settings › Qdrant** draws the warning or info row under the URL and key rows. It probes when it reads a
    changed snapshot, after a key write or a refused write, after a stale-write re-read, and on `r`. Offline
    and `--demo` send no probe and draw no row.
  - **TUI launch:** the first "online" status sends one probe, after `register_all`. A warning queues
    `knowledge search unavailable: <state> — Settings › Qdrant` once per launch, without displacing an earlier
    notice.
  - **Worker start:** one WARN or INFO line, never an ERROR, from a spawned check that is never awaited.
- **Gate step `qdrant`** (D10, Q3). It mirrors TOOL-14's `postgres` step in `gate.sh` and `gate.ps1`: skipped
  when `HTUI_TEST_QDRANT_URL` is unset, failed when the host does not answer. It prints only host:port. Both
  steps parse userinfo up to the last `@`, so a password containing `@` never prints. The htui-dev mod's
  `GATE_STEPS` gained the step.

## Decisions at the gates

- **Routing:** plan, ultracode for implement.
- **CONFIRM:** Q1 cached flag refreshed off the loop (30 s); Q2 a rebindable "why" key, default `ctrl-e`; Q3 a
  `qdrant` gate step, skipped when unset; Q4 an info line for a Qdrant that answers without a key. All four as
  recommended.
- **Accepted deviation (D7):** on a failed search the overlay's bottom-border hint drops `↑/↓ move` for
  `Ctrl+e why`, so the row fits whole at 100 columns (MOD-115 L-E Q5). A failed search shows no hits; `move`
  returns with the hits. A test pins it. The maintainer kept it.
- **Review gate:** `rust-reviewer` in three area instances: store/core/MCP/CLI; workers and app; UI, keys and
  gate. All three approved, with nothing critical, high or medium. The maintainer chose four of the six lows,
  applied in R1:
  - Settings forgets its last probe while the store is offline, so a recovered store probes again instead of
    redrawing the pre-outage warning.
  - Unreadable settings (the `qdrant_url` row or this box's keyring) get their own state, "this box cannot read
    the Qdrant settings", instead of "unreachable" (a new `QdrantCheck::Unreadable`). This departs from the
    blueprint's T2.5 mapping table.
  - `qdrant_live`'s check helper drops its collection before asserting.
  - The worker's spawned start-check handle is renamed so it no longer shadows its function.
  - Not taken: dropping the cause from the Settings "no URL" row, and a deliberate `let _` in the `MemIndex`
    test fake.

## Deviations from the plan (recorded in the blueprint)

- P-1: a shared `concepts.rs` test moved into T1, out of T2/T5's coupling.
- P-2: the in-process URL-write refresh lives in the store loop, not in `qdrant_settings_info.rs`.
- P-7: `ProbeQdrant` also routes through the testkit harness and `try_serve`.
- P-8: the off-loop probe is tested with a paused clock and a delayed `MemIndex`, not a network blackhole.
- T4 keeps an extra `qdrant_warning_noted` flag, so the launch notice is said once even if a later probe
  answer arrives.

## Not verified here

- **Live Qdrant**, owed on the host. The sandbox Qdrant takes 3.5-19 s to create a collection, and the client
  gives up at about 5 s (as for MOD-158):
  - `htui-store` `qdrant_live`: 21 of 28 cases time out at collection or payload-index creation, including the
    new `check_*` and `probe_*` cases;
  - `htui` `qdrant_worker` (`the_worker_job_follows_the_url_row`, `the_worker_job_indexes_a_new_item`);
  - `state_cli_pg`'s `a_search_over_an_index_answers_in_scope`;
  - the lib case `concepts_worker::tests::a_tui_search_of_another_embedders_collection_is_refused_before_the_model`.
- **Windows:** a `gate.ps1` run (the bash self-test passed; the `.ps1` matches by reading).
- **A real launch:** the TUI against a down or keyless Qdrant shows the one status-line notice, and
  Settings › Qdrant shows the row.
- The full gate on the merged tree (`9c1ff47f`, before R1) passed fmt, both clippy runs, the abort grep, the
  migration check, the workflow validator and the plugin. Its test step failed only on the live-Qdrant timeouts
  above and on three tests outside MOD-160's code (`htui-agent` `cli_driver`/`launch` timing, and an
  `agent_worker` Postgres pool timeout). Those three pass when re-run alone.
