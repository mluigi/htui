## What the maintainer can do now

- Read htui's own log in the **Logs tab** at any time, with or without `--log`: sources with line and warning
  counts, a minimum level, follow, and scrolling up pauses it. Set the filter and the log file from
  Settings › Logging, live.
- Read every connected **worker's log** in the same tab, under `workers`, by box, without SSH. Each box's shipping
  level is set from Settings › Boxes.
- See every wait and failure across **all workspaces** in the **activity panel** on the Backlog: needs-you events
  pinned on top and counted in the title, `f` to filter, Enter to jump to the item (switching workspace when
  needed) or to replay a chat, and back to return.

### What was built

- **Migration `0036_activity_event`** (`0034` on the branch, renumbered at the merge behind MOD-150 M3's `0034` and
  MOD-149's `0035`): table `activity_event`, not mirrored. Deferred constraint triggers on `run`,
  `run_step`, `item` and `step_permission` write one event per transition per transaction. Each re-reads the row at
  commit and inserts `ON CONFLICT DO NOTHING` on the unique index `(txid, kind, subject)`.
- **Run park kind:** a plpgsql rule (`judge_failed` / `selection` / `interrupted`) kept in parity with the Rust
  `park_kind` (`htui-core/src/model/activity.rs`). `park_kind` is in turn kept in parity with
  `htui_worker::waiting`.
- **MemStore:** a status-diff hook in `MemStore::write` snapshots the status maps and appends events under the same
  lock. The delete rule lives in `State::remove_project`.
- **Reads:** a narrow `ActivityStore` trait with `MemStore`, `PgStore` and `Writer` forwarding. Pins are derived at
  read time. `ACTIVITY_CASES` (12 conformance cases) run on both stores.
- **Deletion:** an item's or run's events go with it, except failures. Failures keep copied `project_slug`,
  `item_key` and `step_name` and expire at retention.
- **Retention:** shares `log_retention_days` (14 days) and adds 100 000 events per user. The TUI sweeps hourly,
  pruning events and worker logs with one cut. Every worker's shipper sweep prunes events too. The retention
  number is a row in Settings › Prompt (App rung of the typed registry).
- **Panel:** the shell-owned `ActivityPanel` (`htui/src/ui/shell/activity.rs`) fills the activity slot.
  - It holds 500 events and polls about once a second while visible.
  - `[activity]` keys are `enter` (open) and `f` (filter). The focused pane takes every key (`ACTIVITY_BROWSE`), so
    the hidden tab sees none.
  - Enter jumps with history; across workspaces it switches scope first and says so on the status line.
  - The Backlog defaults to the `ide_activity` preset; a saved layout wins.

### Key decisions (plan D1-D13 for detail)

- **D1** One read-only trait, two methods; no append method, since events are written inside the transitions.
- **D2** One writer per transition, in the store: deferred constraint triggers in Postgres, the write-hook diff in
  MemStore. Both see "the final state of the write", so either runtime (the TUI's or a worker's) and the chat path
  write through the same point.
- **D3** Kinds:
  - *needs you*: gate, judge failed, selection, interrupted, unblock, permission;
  - *failures*: step failed, run failed;
  - *plain*: run started, run finished, ready for close-out.
  Text is copied from strings already stored (gate note, permission summary, run failure) and cut to 500 chars.
- **D4** Pins are derived at read time from the subject's current state, never stored. Only the newest needs-you
  event per subject is pinned. A stored `resolved_at` was rejected: waits end on about eight paths, and one missed
  path would leave a stale pin.
- **D5** An event's workspace is the run's `workspace_id`, else the project's owner workspace, else its only
  workspace. Filtering is done in the panel; reads return the user's own rows.
- **D6** Retention is shared with M2's key, with a cap per user. M3 does not wait on MOD-100's sweeper.
- **D7** Deletion with the item is a schema guarantee: `ON DELETE SET NULL` FKs plus `BEFORE DELETE` triggers that
  drop non-failure events. `DeleteReach` is not extended.
- **D8** The panel is shell-owned, one per `App`. A failed read is absorbed, so a down database does not flood the
  status line.
- **D9** Enter reveals the step or replays a chat. A jump to another workspace sets the scope, then reveals.
  History holds no workspace.
- **D10** The keys are in `keys.toml` with a new `Context::Activity`. A shell step in `App::dispatch_key` routes
  keys to the panel while it is focused, unless a modal form on the tab holds them.
- **D11** The Backlog defaults to `IdeActivity`; Logs, Requirements and Skills stay `Ide`.
- **D12** Chat runs write only needs-you (`permission`) and failure events.
- **D13** Out of M3: notifications and bell (MOD-114), `LISTEN`/`NOTIFY` (MOD-46), background workspaces
  (MOD-116), mouse row selection, demo events, search and export.

### Fact-check and blueprint

- The plan fact-check checked 50 claims: 32 verified, 18 amended, 0 falsified.
- Postgres probes (sandbox 18.7, documented the same for 16) found two problems:
  - a combined INSERT/UPDATE trigger with `WHEN (OLD…)` is illegal, so insert and update are separate triggers;
  - re-reading deferred triggers write duplicates when a status moves twice in one transaction, hence the
    `txid`/`subject` guard.
- The architect's F1-F13 were folded into the plan. Among them, F3: the `xmin` guard first planned failed inside an
  `EXCEPTION` block, so the guard uses `pg_current_xact_id()`.
